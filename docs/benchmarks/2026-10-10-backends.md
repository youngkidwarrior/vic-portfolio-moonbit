# JS and Wasm backend benchmark

Run `bun run benchmark` after installing project dependencies and Playwright Chromium. Optional settings:

| Variable | Default | Purpose |
| --- | --- | --- |
| `BENCH_TRIALS` | 10 | Paired samples per backend (2–30) |
| `BENCH_PORT` | 5178 | Local HTTP server port |
| `BENCH_OUTPUT_DIR` | `evidence/benchmark` | Local JSON results and build log |

The harness builds a temporary copy with MoonBit `--release` and cleans up its browsers, server, and copy. Generated JS receives no additional minification. Both backends use the same prerendered HTML, assets, content, and instrumented host on one origin, with precomputed Brotli quality 9 and HTTP no-store. Only the selected backend and matching preload differ. Backend selection and timing instrumentation exist only in the temporary build.

Each pair alternates backend order and uses fresh Chromium processes and contexts. The viewport is 1440×1000 with reduced motion and no CPU/network throttling. Readiness includes runtime loading, content validation, and host initialization; first paint measures static HTML. The harness checks exact HTML/metadata equivalence for all six routes plus 404, changed content, year, isolation, invalid inputs, and recovery. It then warms up 100 render/metadata calls, measures batches of 100 operations, and performs 12 alternating home/résumé navigations per sample. Navigation includes two animation frames.

JSON reports retain individual trials, resource transfers, source/artifact hashes, toolchain versions, and settings. Use a separate output directory to preserve earlier runs.

Content reuse reduces repeated renderer work on both backends. JS renders this small workload faster; cold readiness and frame-inclusive navigation are similar. OS caches, scheduling, JIT and GC effects are uncontrolled, and no significance test was performed. These local desktop measurements do not establish a production/mobile advantage or justify moving browser effects into MoonBit.
