# Optimized backend comparison — 2026-10-10

The current MoonBit/browser boundary remains in place. Content reuse reduces repeated renderer work on both backends. In this local desktop sample, the JS backend completes the small rendering workload faster, while cold readiness and prerendered first paint are similar. These results do not justify moving DOM, navigation, storage, focus, or motion into MoonBit or changing the default backend.

## Method

Run `bun run benchmark` (optional `BENCH_TRIALS=2..30`, default 10; `BENCH_PORT`, default 5178; `BENCH_OUTPUT_DIR`, default `evidence/benchmark`). The script copies the project to a temporary directory, links installed dependencies, builds both targets with MoonBit `--release`, and cleans up its server, browsers and copy. The live runtime and development server are untouched. Generated JS retains the compiler's release output; no additional JS minifier is applied.

Each backend receives the same prerendered HTML, CSS, media, content and instrumented host, served on http://127.0.0.1:5178 with precomputed Brotli quality 9 and no-store. Only the backend selector attribute and matching Wasm fetch / JS module preload differ. Backend forcing and performance marks exist only in the scratch host. The production host retains normal Wasm initialization and JS fallback.

Ten paired trials alternate backend order. Each sample launches a fresh Chromium process and context at 1440×1000, light theme, reduced motion, with no CPU/network throttling. OS filesystem caches and machine scheduling are uncontrolled. This is a local desktop comparison, not a mobile, network, production or language-wide benchmark.

Readiness includes loading both content documents, initializing the runtime, validating content once and wiring the host. FCP measures existing static HTML, not a MoonBit rerender. After readiness and FCP, each sample checks exact HTML/metadata equality for six routes plus 404 against both the old API and the other backend, and verifies changed content, year, isolation, invalid input and recovery. Then 100 render/metadata warm-up iterations precede 100 timed calls per operation. Batched times are divided by 100 to reduce timer quantization; they are microbenchmarks and retain ordering/JIT/GC effects. Finally, 12 alternating home/résumé clicks exercise real host navigation. The navigation metric is the mean per sample through two animation frames, so frame scheduling dominates these tiny rendering costs.

Wasm's compressed renderer is about 4.7 KB smaller here. JS's faster steady render calls do not establish a visible navigation benefit: both route measurements are dominated by browser frames, and no significance test or user-device measurement was performed. The existing stateless API parses both documents twice for a body/metadata pair; the explicit context performs neither parse on repeated calls. Both outputs remain byte-identical.

## Independent verification

Codex repeated two pairs with `BENCH_TRIALS=2 BENCH_PORT=5180 BENCH_OUTPUT_DIR=evidence/benchmark-parent bun run benchmark`. Every runtime/host/content artifact hash and the seven-route output hash matched the ten-pair run. Reused render/metadata medians were 0.0585 ms for Wasm and 0.0225 ms for JS; readiness was 26.9 and 25.2 ms. This small reproduction checks repeatability and does not add statistical significance.

An isolated source copy passed `bun run check` with 12 tests on each backend, then the release build and 27 Chromium browser checks with the existing one-test skip. The first browser invocation failed during discovery because the copy omitted the tracked production-layout fixture; restoring that fixture allowed the unchanged suite to pass.
